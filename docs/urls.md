# URLs are promises

Rule 2. Every address the WordPress site answered is still served, redirected
exactly **once**, or returned as `410 Gone` on purpose. There is no fourth
acceptable answer, and `npm run check:urls` is what makes that true rather than
aspirational.

**Today: 42/42.**

## The three answers

| Answer | When | How |
|---|---|---|
| **Served** | The page exists here | `dist/<path>/index.html` |
| **301** | It moved | A rule in `public/.htaccess` |
| **410 Gone** | It was here and we removed it on purpose | A rule with an empty `to` |

`410` rather than `404` for a retirement, because Gone means "this was here and
we removed it deliberately". A crawler stops retrying it; a 404 gets retried for
months.

### The tag redirects are load-bearing on the front end

Eighteen of the twenty rules point at a **fragment**, not a page. That works
only because three things line up, and breaking any one of them silently
degrades all eighteen to "land at the top of an unfiltered list":

1. `build-redirects.mjs` writes them with Apache's **`[NE]`** flag. Without it
   Apache escapes the `#` and the browser never gets a hash.
2. `TagFilter.astro` renders the filter with `data-tag` slugs matching the
   WordPress tag slugs.
3. `card-filter.ts` reads the hash **on load**, not only on click.

A test pins the first, and the browser test pins the third by visiting
`/faq/#tag=facilitation` and asserting the list is narrowed.

### One tag is misspelled, and stays misspelled

`/tag/preperation/`. The tag normaliser corrects the **display** to
"Preparation". But `tagSlug()` maps it back to `preperation` for the URL,
because that address is live. Fixing the spelling in the URL would break the
redirect the moment it was written. Two unit tests hold both halves.

## Never edit public/.htaccess

It is generated by `scripts/build-redirects.mjs` from two CSVs, and a test fails
if the committed file is not what the generator would write today.

| File | Written by | For |
|---|---|---|
| `data/legacy-redirects.csv` | a person | The addresses the WordPress site answered. |
| `data/retired-urls.csv` | the sync | A slug that changed in Notion. |

The generator resolves chains: if `/a/` → `/b/` and `/b/` → `/c/`, it writes
`/a/` → `/c/`. Two hops is a slower page and a diluted ranking, and the browser
should not have to walk it.

Run `npm run redirects` after adding or renaming content. `sync.yml` runs it in
the same job as the sync, so a rename and its redirect land in one commit rather
than a deploy apart.

## Retiring an address on purpose

Add a line to `data/legacy-redirects.csv` with an empty `to`:

```csv
from,to,why
/some-old-page/,,retired 2026-08; nothing replaces it
```

Then `npm run redirects`. Do not delete it from `data/live-urls.txt`. The point
of that file is that every address the site ever answered is accounted for, and
"deliberately Gone" is one of the three ways to account for it.

## Before pointing the domain here

`npm run build && npm run check:urls` must pass. It does today, on the full
inventory crawled from the Yoast sitemaps. If it ever drops below 42, an address
somebody has linked to has stopped working.

Two things the sitemaps cannot tell you, worth a look before the switch:

- **Search Console** may know addresses the sitemap never listed, old
  attachment pages, feeds, a `?p=` permalink somebody shared.
- **Anything printed**: a slide, a handout, a conference programme. Those never
  appear in any crawl and are exactly the addresses that outlive a redirect.
